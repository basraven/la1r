Codex (in claudecodeui pod) reporting "stream disconnected before completion: stream closed before response.completed" is a **symptom of a litellm /v1/responses mid-stream error**, not a network blip.

**Why:** When the upstream provider errors mid-stream (e.g. deepinfra rejects with ContextWindowExceededError), litellm's `async_data_generator` (proxy_server.py:7627) raises and closes the SSE stream WITHOUT emitting a final `response.completed` event. The OpenAI Responses SDK then reports a premature stream close. The uvicorn access log still shows `200 OK` for these requests (headers are sent before the failure), so non-200 search won't find them.

**How to apply:** To diagnose, grep litellm logs for `proxy_server.py:7627 - .*Exception occured` around the reported time. On 2026-08-23 the cause was ContextWindowExceededError: DeepSeek-V4-Flash-0731 max context = 1,048,576 tokens; a codex request with 664,577 input + 384,000 requested output = 1,048,577 overflowed by 1 token. Failing requests were retried (litellm router num_retries: 2 / retry_after: 5.0 + codex retries), failing identically. Model timeout is 300s — the rejection came within ~4-30s, so NOT a timeout. Related: codex requests `max_output_tokens: 384000`, so any long conversation overflows the 1M window.

Benign log noise not to chase: "Container ownership recording skipped on streaming /v1/responses", "Dropping Responses API tool of type 'namespace'", "register_model ... not in built-in cost map", and "No api key passed in" on GET /v1/models probes (401, from claudecodeui health checks).

**Fix attempt 1 (2026-08-23, INSUFFICIENT):** `kubernetes/development/litellm/config.yaml` sets `model_info: max_input_tokens: 1000000, max_output_tokens: 128000` on deepseek-v4-flash. Verified deployed (configmap == repo == mounted `/app/config.yaml`, GET /v1/models advertises 128000). BUT this is **metadata-only**: litellm 1.96.2's router/responses path passes the client's `max_output_tokens` straight through to deepinfra with NO clamp (checked router.py:8633/9073 — used only for /v1/models listing + model_group_info aggregation; responses/main.py just forwards it). codex 0.149.0 has NO config or catalog key for max output and keeps requesting `max_output_tokens: 384000`, so the error persisted (15:48–15:54, input 664577 + 384000 = 1048577 overflow by 1).

**Root cause of the overflow:** codex honors `auto_compact_token_limit` from its model catalog as the compaction threshold (evidence: request was sent at input 664577 with auto_compact=950000 — if codex used context_window−output it would've compacted at 664576). So with auto_compact=950000, codex lets input grow to ~950k and then requests 384k output → overflow.

**Fix attempt 2 (2026-08-23, EFFECTIVE but limits context):** Lower `auto_compact_token_limit` to **600000** in the codex model catalog `~/.codex/model-catalogs/models.json` (deepseek-v4-flash entry). 600k input + 384k output = 984k < 1,048,576. codex reads the catalog at session start (`model_catalog_json` in config.toml), so next codex session picks it up without a pod restart. Made durable in `kubernetes/development/claudecodeui/init.sh` (new `ensure_codex_catalog` block creates/patches the catalog + adds `model_catalog_json` key; applied via `kubectl apply -k .../claudecodeui/`, takes effect next pod restart). Verify with `codex debug models` (shows auto_compact_token_limit: 600000). Downside: wastes the 1M window (compacts at 600k instead of 950k) and only protects codex.

**Fix attempt 3 (2026-08-23, ROBUST — the one to keep):** litellm **pre-call deployment hook** that clamps the outgoing request. `kubernetes/development/litellm/clamp_output.py` — `ClampOutput(CustomLogger)` with `async_pre_call_deployment_hook` capping `max_tokens`/`max_output_tokens` at `MAX_OUTPUT_TOKENS = 65536`. Registered via `litellm_settings.callbacks: ["clamp_output.clamp_output"]`; mounted at `/app/clamp_output.py` (kustomization includes the file; extra volumeMount/subPath in `litellm.yml`). Works for ANY client through the gateway and preserves the full 950k codex context. **CRITICAL gotcha:** `get_instance_fn` returns the module attribute as-is into `litellm.callbacks`, then calls hooks on it — the module must export an **INSTANCE** (`clamp_output = ClampOutput()`), NOT the class. An unbound class makes hook calls fail with `TypeError: async_post_call_success_hook() missing 1 required positional argument: 'self'` → 500 on every request. Verified: `/v1/responses` with 780k input tokens + `max_output_tokens: 384000` → HTTP 200 (was 400 before); `codex exec` works.

Since the litellm clamp is in place, the `auto_compact_token_limit` can safely go back to **950000** to restore full context (600k was only needed because output couldn't be clamped). Both currently live; no conflict.

NOTE: claudecodeui's proxy-check hits `http://litellm/v1/models` — a curl exit 7 right after a litellm rollout restart is transient (pod still settling); just retry.
